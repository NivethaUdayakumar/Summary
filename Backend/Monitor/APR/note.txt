It knows from the APR_TRACKER status transition, not from watching the CSV directory.

When a run is Await Extraction, the monitor starts the timing subprocess in APR_Utils.py (line 293). That calls TIMING.py through timing_worker() in APR_Utils.py (line 371).

After that subprocess finishes successfully, finish_completed_work() marks the in-memory state as Completed in APR_Utils.py (line 380). STATE_DONE is "Completed" in APR_Definitions.py (line 25).

On the same monitor cycle, update_apr_tracker() submits that tracker row to the SQLite writer in APR_Utils.py (line 323).

The actual trigger is in process_tracker_update() in APR_DB_Operations.py (line 465). It:

reads the previous DB status with get_tracker_status_record() at APR_DB_Operations.py (line 295)
upserts the new APR_TRACKER row
only if the new row is Completed and the previous one was not Completed, it calls sync_tracker_timing_csv() at APR_DB_Operations.py (line 452)
sync_tracker_timing_csv() builds the expected CSV path from the run scope in APR_DB_Operations.py (line 280), checks that the CSV exists, reads it, then write_timing_stage() in APR_DB_Operations.py (line 434) does:

delete old rows for that Job/Milestone/Block/Stage scope via APR_DB_Operations.py (line 318)
insert APR_TIMING_DETAIL via APR_DB_Operations.py (line 325)
compute and insert APR_TIMING_SUMMARY via APR_DB_Operations.py (line 419)
So the short answer is: the DB writes timing detail/summary when the tracker row first becomes Completed, and at that moment it looks for the stage CSV and loads it.

One important caveat: there is no background scan of APR_RUNS anymore. If the CSV did not exist exactly when that first Completed tracker update happened, this path would skip it and not retry automatically. The current design assumes TIMING.py has already finished writing the CSV before the status flips to Completed.
