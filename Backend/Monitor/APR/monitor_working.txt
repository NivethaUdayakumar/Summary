APR Monitoring Process

1. FLOW_MONITOR.py starts the APR flow once with FLOW and PROJECT_CODE from sys args.
2. APR_MONITOR_ITEMS.build_context creates the long-lived runtime context for that project.
3. Every monitor loop, APR_MONITOR_ITEMS.get_runtime_paths rebuilds absolute paths from APR_VARS.py.
4. APR_VARS.py is reloaded on demand, so edits to batch size, poll time, stages, paths, and other settings are picked up without restarting the monitor.
5. The monitor refreshes the logger, state file path, force-extract JSON path, and tracker writer path each cycle.
6. The state file is loaded fresh each cycle. Only persistent run fields are stored there; worker queues and subprocess objects are kept only in memory.
7. The force-extract JSON is read from /proj/<project_code>/DashAI/APR_FORCE_EXTRACT.json and normalized into items with keys job, milestone, block, and stage.
8. IMP run directories are scanned using absolute paths and the configured depth / flow / tool filters.
9. Stage log files are discovered for each configured APR stage.
10. APR_ITEM_STATUS computes the tracker status for each log using current file metadata, persisted state, and whether that run is already in a batch.
11. Runs in "Await Extraction" are validated before batch submission. Missing KPI files are marked with ERR002 and move to "Job Failed"; missing timing reports are marked with ERR003 and move to "Extraction Failed".
12. Valid runs in "Await Extraction" are queued into the batch runtime owned by APR_STATUS_ACTION.
13. Pending runs are grouped into batches of APR_VARS.BATCH_SIZE.
14. At most APR_VARS.MAX_PARALLEL_BATCHES batch subprocesses run at the same time.
15. If the pending queue does not reach BATCH_SIZE within APR_VARS.BATCH_RUN_WAIT_TIME seconds, the current pending count is launched as a short batch in any free parallel slot.
16. The monitor manages EXTRACTORS/BATCH_COMMANDS so it contains one batch command file per configured parallel batch slot.
17. When the parallel-batch count is initialized or safely reset with no active batches, existing managed batch command files are deleted and recreated.
18. Each submitted batch rewrites one slot file, for example EXTRACTORS/BATCH_COMMANDS/BATCH_COMMAND_1.txt, so line 1 is:
    module load Python3/3.11.1
    and each remaining line is one extractor command:
    python3 <abs_path_to_APR_TIMING_INNOVUS.py> <project_code> <stage> <run_dir>
    subprocess.Popen then launches:
    utilq -Is source <abs_path_to_slot_batch_file>
19. When a batch is submitted, all its runs are marked as "Extracting" in memory, persisted state, and tracker SQLite immediately, and one batch submission log line is written.
20. On every monitor cycle, and again while item statuses are being computed, running batches are checked for existing DashAI timing DB files.
21. As soon as any in-flight runs have timing DBs, all matching runs move to "Completed" immediately and their tracker rows are refreshed without waiting for the rest of the batch process to finish.
22. When the batch process exits, any remaining unresolved runs are classified: the first missing run becomes "Extraction Failed"; later missing runs are returned to "Await Extraction" for retry.
23. APR_UPDATE_TRACKER applies KPI extraction from EXTRACTORS/APR_KPI_EXTRACT.py and submits tracker rows to SQLite. Completed runs stay "Completed"; if KPI values are blank, the tracker keeps comment ERR002 and Promote=no.
24. Tracker comments use ERR001 for generic job failure, ERR002 for missing KPI data, and ERR003 for missing timing reports. Persisted ERR001 and ERR002 runs stay in "Job Failed", while ERR003 runs stay in "Extraction Failed" until the source files change.
25. APR_DB_ACTIONS refreshes tracker schema dynamically, so new KPI columns can be added while the monitor is running. Existing rows keep blank values for new text columns until updated.
26. Completed force-extract requests are removed from the JSON file after those runs finish, even if other runs from the same batch are still in flight.
27. If the monitor is stopped, runs that already reached "Completed" stay complete; only unresolved "Extracting" or pending batch items are reset back to "Await Extraction" during cleanup.
28. APR_UPDATE_LOG only writes batch-level log lines: submitted count, completed count, success count, and failed count.
