How The APR Monitor Actually Moves A Run

This page mirrors the current APR monitoring code path. It focuses on the main loop, item-status rules, batch queueing and submission, per-item completion during a running batch, and shutdown behavior through bjobs / bkill.

Main Rule

A run becomes Completed only when both outputs exist: the source DB under the IMP run directory and the timing DB under DashAI APR_RUNS. If the log becomes newer than the timing DB, the run returns to Await Extraction.

Main Flow

The shared FLOW monitor calls the APR modules in this order for every cycle and every discovered log item.

1

Get Items

APR_MONITOR_ITEMS refreshes runtime paths, loads state and force-extract payloads, reconciles running batches, persists dirty runtime data, and discovers log files.

2

Compute Status

APR_ITEM_STATUS parses the log, reads file metadata, checks source and timing outputs, and computes both status and the base tracker comment.

3

Batch Action

APR_STATUS_ACTION validates Await Extraction items, queues them, forms batches, submits slot files, and marks submitted runs as Extracting.

4

Tracker Update

APR_UPDATE_TRACKER fills KPI fields for Completed runs and pushes the tracker row into SQLite through the writer thread.

5

Batch Log

APR_UPDATE_LOG keeps only batch-level logging: submit, complete, and terminate events.

6

Persist State

APR_UPDATE_STATE stores the new state entry back into the shared JSON state file only when changes happened.

Batch Lifecycle

The extraction side is queue-driven. Runs move from Await Extraction into a FIFO queue, then into slot-backed batch files, then into active running batches.

Queue

  1. Only items with computed status Await Extraction enter batch handling.
  2. Validation happens first: missing KPI file -> ERR002, missing timing reports -> ERR003.
  3. Valid items are inserted into pending_items only if they are not already pending and not already running.
  4. The queue is an OrderedDict, so extraction order is FIFO.

Form And Submit

  1. If pending count reaches BATCH_SIZE, launch immediately.
  2. If it stays smaller, wait until the oldest item ages past BATCH_RUN_WAIT_TIME, then launch a short batch.
  3. At most MAX_PARALLEL_BATCHES can run at once.
  4. Each batch claims one reusable slot file such as BATCH_COMMAND_1.txt.

Reconcile

  1. Every cycle, running batches are checked before the submit process exit code matters.
  2. If any item already has both outputs, it flips to Completed immediately.
  3. When the batch process exits, the first unresolved item becomes Extraction Failed.
  4. Later unresolved items go back to Await Extraction for retry on the next cycle.

Status Rules

These are the high-level decision buckets used when APR_ITEM_STATUS computes one log's status.

Completed

Both outputs exist: source_db_exists and timing_db_exists. The log must not be newer than the timing DB.

Await Extraction

Used when: force extract is set, source DB exists but timing DB does not, the log is newer than the timing DB, or an unfinished batch item is retried.

Extracting / Job Running

Extracting means the run is already part of a submitted batch. Job Running means neither output exists yet and the log still looks active by age.

Failed States

Job Failed covers generic source-side failure and persisted validation failures. Extraction Failed covers missing timing reports or the first failed item in a finished batch.

Tracker comments are intentionally simple: -, ERR001, ERR002, ERR003, or QC PASS. Completed runs stay Completed even when KPI extraction later decides the KPI content is incomplete; in that case the comment becomes ERR002 and Promote=no.

Runtime Structures

The monitor keeps persistent run state on disk, but queues and submit-process objects stay in memory.

pending_items

  • FIFO extraction queue
  • Contains lightweight batch items
  • Used to form full and short batches

running_batches

  • One record per submitted batch
  • Stores batch id, slot file, submit command, process, items, and state keys
  • Updated as items finish early

available_batch_slots

  • Pool of reusable BATCH_COMMAND_n.txt files
  • Claimed on submit
  • Released when a batch exits or is terminated

_ACTIVE_BATCH_PROCESSES

  • Fallback map of local submit Popen objects by PID
  • Used so shutdown can still find leftover local processes
  • Not the main batch model

Shutdown And Recovery

APR_CLOSE asks APR_STATUS_ACTION to terminate active work carefully, while preserving already-complete runs.

LSF Lookup

The monitor scans LSF jobs using the stored slot file path or stored submit command so it can map a running batch back to a JOBID.

bjobs -o "JOBID COMMAND"

Termination

If a matching job is found, the monitor records the job id and issues bkill. It then still tears down the local submit process tree as a fallback.

bkill <JOBID>

Per-Item Outcome

  • If both outputs already exist, keep Completed.
  • If still unresolved, reset to Await Extraction.
  • Pending-but-never-submitted items also return to Await Extraction.
The practical outcome is that the monitor is optimistic about work that already produced the needed artifacts, but conservative about anything still in-flight. On restart, unresolved runs naturally re-enter the batch queue through the normal status path.
