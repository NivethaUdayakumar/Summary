Runtime Loop

The shared FLOW monitor calls the APR modules in a fixed order. The key idea is that live files drive the status, while persisted state only carries the minimal fields needed for retries and extraction history.

1

APR_FLOW_CONTEXT

Creates runtime directories, loads APR_STATE.json, resets Status and Comments, starts the SQLite writer, and appends monitor_started to the log.

2

APR_MONITOR_ITEMS

Refreshes finished batches first, then discovers APR run directories and stage log files under IMP.

3

APR_ITEM_STATUS

Computes one item's status from source DB, timing DB, KPI file, timing reports, log age, and the light saved state entry.

4

APR_STATUS_ACTION

Queues only Await Extraction items, forms batches, writes one unique batch file, submits it through utilq, and marks the items Extracting.

5

APR_UPDATE_DB

Saves the changed state entry back into APR_STATE.json and upserts the APR_TRACKER row.

6

APR_SLEEP

Waits for the next cycle using POLL_SECONDS, while still checking once per second for a stop request.

7

APR_CLOSE

Only closes the shared SQLite writer cleanly before the FLOW monitor exits.

Status Logic

Status is recomputed on the fly. The saved state is used only to preserve Last_Extract_Submission, Rerun, and whether an item is still in an in-flight extraction.

Completed path

Source DB and timing DB are both present

  • If the timing DB is newer than the source DB, extraction is treated as complete.
  • If the KPI file exists, status becomes Completed with comment QC_PASS.
  • If the KPI file is missing, status becomes Job Failed with comment ERR002.
Re-extract path

Source DB exists but timing output is stale or missing

  • If the prior saved status is Extracting, keep it as Extracting.
  • If timing reports exist, move to Await Extraction with comment -.
  • The Rerun count increments only when a stale timing DB is being retried.
Still active

Source DB does not exist yet

  • If the log file still looks recent within RUN_ACTIVE_TIME, the item stays Job Running.
  • This path does not trigger extraction because the source-side output is not ready yet.
Failure path

Missing artifacts with no valid next step

  • ERR001: source DB never appeared and the log no longer looks active.
  • ERR003: extraction is needed but timing reports are missing.
  • ERR002: timing DB exists but KPI output is missing.
No force-extract path exists anymore. If a run needs to be extracted again, deleting the timing DB is enough for the normal status logic to send it back to Await Extraction.

Batch Lifecycle

The action module keeps runtime memory small. Pending work and submitted batches are the only in-memory structures; the durable state still lives in APR_STATE.json.

Queue

Collect only what is ready

  • Only items already computed as Await Extraction enter the queue.
  • Duplicate items are skipped if they are already pending or already inside a running batch.
  • The queued payload is intentionally minimal: stage, run directory, log path, and state key.
Submit

Create one dynamic command file per batch

  • Each batch gets a unique filename under EXTRACTORS/BATCH_COMMANDS.
  • The file is populated with the Python module load and one extractor call per item.
  • After submission, every batched item is saved as Extracting with a new Last_Extract_Submission timestamp.
module load Python3/3.11.1
python3 APR_TIMING_INNOVUS.py <project_code> <stage> <run_directory>
utilq -Is source APR_BATCH_COMMAND_<uuid>.txt
Reconcile

Clear temporary extraction state

  • When the submit subprocess finishes, the generated batch file is deleted.
  • Each batch item has Status and Comments reset to null so the next cycle recomputes them cleanly.
  • Extract_Completed is refreshed by comparing the timing DB timestamp against the source DB timestamp.

State Model

The APR monitor keeps the persisted state intentionally small. It is just enough to remember the extraction lifecycle without caching large runtime structures.

Context

Core runtime context

  • flow
  • project_code
  • db_writer
  • state
Per item

Only five state fields are saved

  • Status
  • Comments
  • Last_Extract_Submission
  • Extract_Completed
  • Rerun
Startup rule: whenever the monitor restarts, every saved state entry has Status and Comments reset before polling begins. That guarantees the new runtime re-evaluates live status instead of trusting stale process memory.

Files Written

The current implementation writes only the artifacts needed for monitoring, extraction, and tracker updates. There is no separate state-update or log-update module anymore.

Persistent

Project runtime outputs

  • DashAI/STATE_FILES/APR_STATE.json
  • DashAI/APR_LOGS/APR_YYYYMMDD.log
  • DashAI/DashAI_APR.db with APR_TRACKER
  • DashAI/APR_RUNS timing DB outputs from the extractor
Ephemeral

Batch command files

  • Created under EXTRACTORS/BATCH_COMMANDS with a unique UUID-based name.
  • Used only to launch the extractor batch through utilq.
  • Deleted after the submit subprocess finishes.
